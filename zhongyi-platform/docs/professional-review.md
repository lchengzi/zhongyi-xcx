# 专业资格与固定版本审校记录

当前工作台可以登记人工资格核验依据，并让独立人员对已经通过编辑审阅的单个食材教育草稿记录意见。记录始终私有，不改变小程序历史目录，也不提供发布按钮。后台角色不是专业资格，软件记录不是执业证认证；真实身份、适用执业范围、证据和人员同意仍须由负责的管理员在线下核实。

## 范围与状态

本阶段只处理 `ingredient_education`。中医师和药师两类独立意见是本项目的保守内容治理策略，不是关于法律必需人数的结论，也不能批准整方、照片、诊疗或用药指导。当前一个账号使用一类有效资格，两类意见须来自不同人员。

资格依据分为 `manual-verification` 和 `test-fixture`。前者要求真实外部核验依据；后者专供隔离工程测试，即使两类测试意见均通过，也永远不能满足真人审校门槛。本次自动化没有制造真人资格、签名或医学批准。

| 返回状态 | 含义 |
| --- | --- |
| `pending` | 缺少当前固定版本的有效意见 |
| `changes_requested` | 当前专业意见退回；需要新正文修订和独立编辑审阅 |
| `recorded` | 已有内部通过记录，但资格、独立性或真实依据条件不齐备 |
| `eligible_for_publication_approval` | 两类不同人员的当前有效人工核验意见齐备，仍需单独发布批准 |

所有状态均返回 `visibility=private`、`publicationEnabled=false`。原有草稿字段 `professionalReviewState=pending` 保持不变；调用方应读取新审校详情，不把编辑通过或测试意见当作发布授权。

来源登记目前仍标为待核验。专业意见齐备也不能替代目录准入、来源适用范围、图片授权或安全规则的发布检查；这些必须在后续版本化发布门禁中分别处理。

## 界面操作

管理员在“账号权限”创建独立审阅账号，再进入“内容协作 → 专业审校记录”。选择资格所属账号、类别、依据类型、内部核验依据编号、UTC 截止时间，填写说明并明确确认。不要输入身份证、证件原图或用户健康信息。管理员不能给自己登记核验通过；普通编辑没有资格管理入口，非管理员只能读取自己的资格历史。

专业人员登录后搜索食材，核对固定正文、摘要、来源版本及原文定位，再填写通过或退回意见。服务端检查完整正文、固定来源和编辑审阅参与历史，参与过此条目的整理或编辑审阅者不能再专业自审，即使其参与记录已经超出界面最近 20 条。

资格撤销、过期、账号停用/权限版本变化，以及新资格版本，都会使此前意见失去当前效力。重新核验不会自动复活旧意见；如旧通过意见仍在，先由原审校人或管理员撤销，再重新审校。已退回正文不能原版本直接改为通过，应保存新正文并重新完成编辑审阅。撤销保留原历史，不要求已经过期的资格重新生效。

多人操作携带当前资格、正文和审校协作版本；过期写入返回 409，不覆盖其他人员的意见。网络失败或冲突保留当前输入；刷新或离开前，界面提示确认放弃未保存内容。

## API 与数据库

接口均位于 `/api/v1/editorial`，要求账号会话；写入额外要求可信 Origin 和 CSRF 令牌，不开放匿名或本地编辑密钥通道。

| 接口 | 输入与权限 |
| --- | --- |
| GET `/qualifications/:userId` | 仅本人或管理员，返回 `{userId, items}`，最近20条资格版本，空历史也包含所属账号；不接受查询参数 |
| POST `/qualifications/:userId` | 仅管理员；`{qualification, expectedRevision}`，成功 201 |
| GET `/professional/:id` | 已登录账号；响应显式含ingredientId（无草稿也包含），以及固定草稿、最近20条意见、各专业最新意见、当前协作号和失效原因 |
| POST `/professional/:id` | `{profession, decision, contentRevision, contentDigest, expectedLockVersion, expectedReviewVersion, expectedQualificationRevision, comment}`；成功 200 |

`qualification` 精确接受 `profession/status/evidenceKind/evidenceReference/validUntil/comment/verificationConfirmed`；时间采用完整 UTC ISO 字符串。通过或退回必须由持有当前对应资格的启用管理员/审阅账号执行；撤销仅限原审校人或管理员。意见正文最多 1000 字，依据编号最多 200 字；未知字段拒绝。前端按钮不是权限边界，仓储事务内再次检查账号与会话。

专业记录阶段的 SQLite v6 / PostgreSQL v4 追加 `professional_qualifications` 和 `professional_reviews`，当时共 23 张业务表；PostgreSQL 另有 2 张迁移历史表和原有 3 个序列。资格主键是账号/修订；意见主键是食材/审校版本，外键关联正文和资格的固定版本。每行绑定规范化 SHA-256 摘要；更新/删除被数据库触发器拒绝，PostgreSQL 还拒绝 TRUNCATE。此保护不抵抗有 DDL 权限的数据库管理员。

后续来源核验阶段追加 SQLite v7 / PostgreSQL v5，总计 24 张业务表；发布治理阶段继续追加 SQLite v8 / PostgreSQL v6，总计 28 张业务表。本节旧版本与下方旧轮次保留为历史，不代表当前运行版本。来源检查和发布快照不改变专业意见绑定的正文摘要，见 [来源核验](source-verification.md) 和 [发布治理](publication-lifecycle.md)。

SQLite 写事务使用 `BEGIN IMMEDIATE`；PostgreSQL 使用既有 schema 业务锁，取得锁后重新检查资格、账号和版本，因此排队期间的撤权不会被旧请求绕过。界面历史只显示最近 20 条，授权判断使用完整记录，并单独提供各类最新意见。

## 迁移与恢复

该阶段新增 SQLite v6 的 23 表快照格式 v4，保留旧 v3/v4/v5 支持。旧源文件不被升级，原迁移日志、时间、导入摘要和序列高水位保留。当时旧 PostgreSQL v1/v2/v3 须先备份并停写，再显式升级到 v4；现行运行要求 v6，操作以 [迁移说明](postgres-migration.md) 为准，启动不自动加表或回退 SQLite。

该阶段 PostgreSQL v4 加密业务备份覆盖新增资格/意见。原 PostgreSQL v3 的 21 表备份保持兼容：恢复时重建原 v3，而不伪造原备份中不存在的日志；操作者另行显式升级后，新增表从空表开始。当前 v6 同时兼容原 v4/23 和 v5/24 表备份，新增发布冻结与恢复校验也不改写旧记录。操作说明见 [迁移](postgres-migration.md) 和 [备份恢复](backup-recovery.md)。

恢复保留的是备份时点的资格与意见，不证明它们在恢复时仍获外部认可。当前 v6 恢复已追加新的发布冻结批次，仍须核对备份后撤销、账号变更及专业资格现状；恢复冻结状态本身不会复活旧批准或指针。后续发布 API/页面已经接入，操作以[发布治理](publication-lifecycle.md)为准；接入不等于取得真实审校或发布授权，本轮新增资料仍私有。
