# 来源核验与发布前资料检查

工作台可为固定来源版本登记独立查证记录，并检查单个食材教育草稿是否具备必要的来源与专业意见。这补齐 P0 的资料治理及 P4.2 发布流程的前置条件，**不实现发布批准、正式内容快照、撤回或回滚**。新资料保持私有，匿名接口仍只返回已导入的 2026 年 8 月目录快照。

## 来源与正文版本

每条核验绑定来源 ID、修订与 SHA-256 摘要，记录查证时间、复核截止时间、内部依据编号、说明、适用食材及原文支持的信息域。信息域分为身份、食用部位、加工形态、安全边界、目录适用范围；选择一个食材不代表来源自动支持其全部信息。

核验历史独立保存在 `source_checks`，不修改原 `ManagedSource.verificationState=pending` 接口契约或已存在的内容摘要；该状态不是 `source_versions` 的数据库字段。新来源版本从未核验起步；旧正文引用的固定来源版本保持可追溯，仍需检查该固定版本的核验是否过期、撤销或失效。核验历史仅追加；退回、撤销和重新查证都产生新记录，不覆盖原意见。

同一来源使用全局核验协作版本，写入须携带 `expectedVersion`。界面展示最近 20 条记录，但固定来源版本的最新核验从完整历史读取，不因落在展示窗口之外而丢失。

## 独立性和人工责任

启用的管理员或审阅账号可以登记通过/退回，但参与过该来源任一版本整理的账号不能自行核验。撤销仅限原核验人或管理员；编辑只能查看。服务端在数据库写事务内重新检查账号角色、启用状态、账号版本和会话，等待其他写入期间被停用的账号不能继续提交。

`manual-check` 是人工查证声明，软件不访问、认证或自动判断来源网页是否权威。`official` 类别需要实际官方依据，选择该选项不能把测试网址变成官方资料。查证日期不能在未来，核验通过必须明确确认且复核期限尚未到期。软件判定当前有效，也不代替真实原文核对、专业审校或发布责任人的决定。

`test-fixture` 只能验证工程流程，界面显示“仅工程测试核验”，不能满足发布条件。真实身份、资料内容和来源权威性仍需由人员核实。本轮数据库及浏览器夹具只写明确的测试记录；人工查证齐备的正向策略测试只在内存中构造，不登记为实际完成查证。

核验不授予原文转载、照片使用或整方发布权；照片的身份、部位、加工形态和授权须继续单独审核。只登记内部依据编号和必要说明，不上传证件或健康信息。

## 发布前检查

`readyForReleaseApproval=true` 仅表示以下软件前置条件齐备，不是发布权限：

- 当前固定草稿已通过独立编辑审阅，食用部位、教育说明和安全边界非空。
- 具备两类不同人员的当前有效人工专业意见；工程测试资格/意见不能替代。
- 所有引用来源均有当前有效的人工核验，并明确覆盖该食材。
- 有效引用合计支持全部五类信息，且目录适用范围至少有一条标为官方的实际人工核验依据。

检查在同一数据库读取事务中获取正文、专业意见和引用核验，返回正文摘要、协作版本、专业审校版本及各来源核验版本/摘要。缺口直接列出；没有风险记录或没有找到来源不能解释为内容安全。

结果始终为 `visibility=private / publicationEnabled=false`。后续发布内核已绑定固定快照并重新核对权限、期限、来源和专业意见，也已接入数据库恢复冻结；发布 API 和页面仍待接入，见 [发布治理](publication-lifecycle.md)。资料检查结果不是长期授权，不能缓存一个通过结果后跳过重新检查。

## API 与界面

路径相对 `/api/v1/editorial`，仅账号模式可用；写请求沿用可信 Origin 和 CSRF 校验。请求上限 32 KiB，未知字段拒绝。

| 接口 | 契约与权限 |
| --- | --- |
| GET `/source-checks/:id/:revision` | 已登录账号读取固定来源、最近历史、固定版本最新意见和失效原因；拒绝查询参数 |
| POST `/source-checks/:id` | `{check, expectedVersion}`；管理员/独立审阅者写入；并发版本过期返回 409 |
| GET `/publication-preflight/:id` | 已登录账号只读检查；拒绝查询参数，不改变审批或公开状态 |

`check` 精确接受 `sourceRevision/sourceDigest/decision/evidenceKind/ingredientIds/domains/authority/checkedAt/validUntil/evidenceReference/comment/verificationConfirmed`。UTC 时间采用完整 ISO 字符串；范围为 1–200 个已知且不重复的食材、1–5 个不重复信息域；依据编号最多 200 字，说明最多 1000 字。决定为 `verified/return/revoke`，来源类别为 `official/research/reference`。

在“内容协作 → 来源核验与发布检查”中选择来源及修订，填写范围和查证依据；来源核验与食材发布前检查在同页分区。请求失败或冲突保留输入；刷新、切换来源/页签前确认是否放弃未保存内容。没有发布按钮。响应状态为 `pending/verified/returned/revoked/expired/invalidated/recorded`，分别表示缺少、人工记录有效、退回、撤销、过期、权限/依据失效或仅测试。

## 数据库与恢复兼容

SQLite v7 / PostgreSQL v5 引入 `source_checks`，当时有 24 张业务表；后续发布治理追加 SQLite v8 / PostgreSQL v6，总计 28 张业务表，另有 PostgreSQL 两张迁移历史表和原有三个序列。来源核验主键为来源/核验版本，复合外键固定来源修订，操作者关联账号。每行规范化摘要检查范围、时间及固定关系；SQLite 禁止更新/删除历史，PostgreSQL 还禁止 TRUNCATE。这不是抵抗有 DDL 权限的数据库管理员的保证。

只读迁移现支持 SQLite v3 至 v8，对应快照格式 v1 至 v6 和 16/18/21/23/24/28 表。旧源文件不升级，不改历史导入摘要或序列。新业务代码要求 PostgreSQL v6，已有旧库须先备份并停写，再显式升级，不自动加表或回退 SQLite。

当前 AES-256-GCM 业务备份覆盖全部 28 表与历史/序列；兼容 PostgreSQL v3/21、v4/23 和 v5/24 表备份。旧备份先恢复为原结构，再显式升级，新表为空，不补造历史核验。v6 恢复到全新 schema，完整校验后撤销旧会话并追加新发布冻结批次，不覆盖原库或自动切流。冻结恢复后仍需重新批准并明确发布；备份后的实际撤销和人员资格须另外核对。详见 [迁移](postgres-migration.md) 和 [业务恢复](backup-recovery.md)。

完整复现入口为 `npm.cmd run ci:verify`、`ci:postgres`、`ci:browser`、`ci:postgres:browser` 和 `ci:https`。本机检查不替代远程 Actions、Docker、公开 HTTPS、专业签审或安卓/iOS 微信真机验收。本阶段没有真实来源查证、照片公开、整方公开、真实模型调用、生产迁移或对外发布。
