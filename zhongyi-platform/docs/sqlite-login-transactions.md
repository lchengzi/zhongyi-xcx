# SQLite 登录限流事务与耗时验证

SQLite 登录现在把过期计数清理、IP计数和账号计数放在同一个短事务内，密码校验在该事务提交后执行，会话与成功安全事件仍在另一事务内提交。普通成功登录的计数和会话写入由三个提交边界减为两个；没有降低密码算法、持久性或测试超时。

这是依据隔离测量实施的事务优化，不是对历史HTTPS超时根因的完整证明，也不是线上性能指标。

## 测量证据

`npm.cmd run profile:login` 先构建当前服务端，再新建 `.local/login-profiles/run-*`、专属SQLite文件和随机测试密码，使用实际编译的 `AuthRepository` 连续登录六次。它不读取工作库环境、不启动生产应用、不连接模型、不更改PRAGMA，也不删除历史报告。工具结束后检查六份会话、两份计数均为6，再关闭数据库。

计时代理只包装本轮传给仓储的数据库对象，不修改全局原型或生产应用。报告保存固定操作分类、开始/结束/耗时、是否处于显式事务及失败布尔值；不保存SQL、绑定参数、查询结果、用户名、密码、令牌或原始异常。最多128条SQL操作，超出时本次测量不能通过。`passwordCheckGapMs`是账号查找完成到首次账号重查开始的间隔，含密码派生、比较和调度，不是纯密码算法CPU耗时。

两轮均为本机编译SQLite、`journal_mode=delete`、`synchronous=2`、`busy_timeout=3000`，数据库已关闭；数据文件互相隔离。修改前两份计数各在显式事务外执行，单次写入约471–1225ms，成功会话提交约418–1595ms，SQL占主要耗时。修改后的限流写入在同一显式事务内，成功登录仍保留独立会话提交。

两轮不是随机交错或相同机器负载的受控基准。修改前后的耗时差不能全部归因于事务合并，不能据此宣称固定倍数提升、生产延迟或QPS。现有HTTPS失败记录只定位到等待响应头；没有对应请求内部SQL时序，因此不能把这些新测量倒填到历史请求。[请求阶段与失败证据](https-request-diagnostics.md)

SQLite会为没有显式事务的数据库操作启动隐式事务；显式事务把修改保留到提交或回滚，持久化提交也可能涉及日志和数据文件同步。减少不必要的提交边界与关闭同步不是同一种优化。[SQLite事务](https://www.sqlite.org/lang_transaction.html)、[SQLite原子提交](https://www.sqlite.org/atomiccommit.html)

## 限流和失败行为

IP仍为50次/15分钟，账号仍为10次/15分钟，成功与失败尝试都计数；同时最多4次密码验证。密码仍为每账号独立盐与原scrypt参数，会话、Cookie、Origin、CSRF和角色校验未改。

账号达到限额时，已增加的IP计数仍提交，再返回429；IP达到限额时不再增加另一个账号计数。过期清理只执行一次，和计数一起提交。实际数据库写入或提交失败则整体回滚并拒绝登录，不创建会话；后续有效请求可以继续使用该连接。并发容量拒绝仍发生在计数提交后，不退还次数。

限流事务不跨越异步密码计算，不把IP计数与会话成功事务合成一个长事务。后续密码错误仍保留已提交尝试计数；数据库错误不当成正常限流拒绝，不吞掉失败返回成功。
