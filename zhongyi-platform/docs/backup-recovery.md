# PostgreSQL 业务备份与恢复

这是 P4 的应用业务逻辑备份工具，不是数据库集群灾备，也不代表已上线。正式运行入口不提供备份 HTTP API；只有持有数据库权限和独立备份密钥的操作者可执行离线命令。测试只操作独立工程夹具，不迁移或恢复真实工作库。

容器入口另有[独立密钥文件与归档恢复](container-backup-recovery.md)：仅一次性备份/恢复服务接收密钥，导出目录可写、恢复输入只读，文件被限制在专用挂载内；编译入口已在独立PostgreSQL演练。下文宿主CLI仍使用安全环境密钥，不能将主机恢复结果当作真实Docker挂载或卷恢复。

## 覆盖范围和限制

- 当前 PostgreSQL v10 schema中的32张业务表、`postgres_migrations`、`migration_runs`，以及 3 个事件序列高水位。包括专业图片意见及固定资格/原图/核对/送审/权利的摘要和撤销历史；独立图片权利审核的固定送审引用、具名审核人、依据、署名/修改方案、有效期与撤销历史；图片送审版本、当次意见固定引用，以及图片核对意见及候选元数据/摘要历史（不含原图字节）；固定快照、独立批准、发布事件和冻结历史；包含账号散列、私有草稿、固定来源版本、来源核验、审阅记录、专业资格核验/意见、外部许可历史及已消耗的调用额度；它们都是敏感数据。兼容旧 PostgreSQL v3 的 21 表、v4 的 23 表、v5的24表、v6的28表、v7的29表、v8的30表和v9的31表备份，不忽略未知表/字段。新增权利历史还须通过版本、送审摘要、审核人独立性及撤销前序关系校验；备份通过不授予图片公开资格。
- 保留原 SQLite v3 至 v12 日志及原导入摘要、计数、时间，不把 PostgreSQL 升级伪装成 SQLite 迁移。原导入计数是历史值，不要求等于之后的业务行数。
- 仅接受完整已知表和字段，发现缺表、未知表/字段、目录摘要或迁移摘要异常即拒绝。不接纳任意 SQL；恢复使用项目中受信且版本固定的 DDL。
- 不复制自定义 DDL、视图、额外索引/触发器、集群账号/权限、扩展、服务器设置、媒体、密钥、日志或 WAL。不提供时间点恢复、跨区域副本或自动故障切换。自定义对象必须另行登记与备份，不能把本工具当作它们的保护措施。
- 单份明文业务数据上限 32 MiB，加密文件读取上限 48 MiB，内存处理不适合大库。增长后应改用受控原生备份工具及恢复演练，不能仅调大上限。
- 当前仅支持 PostgreSQL 业务库。SQLite 保留用于本机演示，但尚无同等验证的加密恢复工具；不能声称已覆盖 SQLite 灾备。

## 一致性和加密

捕获前先取得与导入/升级、业务写入共用的两把维护锁，再开启只读可重复读事务。正常业务写操作在捕获期间等待，读操作可继续；短锁等待/语句截止失败会拒绝备份并释放专用连接。序列并非 MVCC 快照，因此不能只依赖可重复读保证序列一致性。运维时应停写并禁止手工 DDL/直接 SQL；不遵守项目锁协议的外部写入无法由此工具阻止。[PostgreSQL 事务隔离说明](https://www.postgresql.org/docs/18/transaction-iso.html)

文件使用 AES-256-GCM、每次随机 12 字节 IV、认证标签和绑定格式的附加认证数据。整份业务数据与历史使用独立规范化 SHA-256 摘要校验；摘要不是替代密钥认证的安全签名。错误密钥、被改写或不完整文件一律拒绝；备份过程不创建明文临时文件。源数据库本身、内存和宿主环境仍需独立访问控制与存储保护。[Node.js 加密接口](https://nodejs.org/docs/latest-v22.x/api/crypto.html)

通过安全环境配置 `BACKUP_ENCRYPTION_KEY`（32 字节随机密钥的标准 Base64）和 `DATABASE_URL`。没有默认密钥，不在参数、日志或聊天中提供真实值。密钥应由操作者通过可信秘密管理方式生成、独立保管并验证可恢复；丢失密钥无法解密。更换密钥后仍须保管旧备份所需旧密钥。本工具不自动建立密钥托管或轮换制度。

输出目录必须已存在且受限，不经过符号链接或 Windows junction；输出文件使用独占创建，不覆盖已有文件。Unix 请求文件模式 0600；Windows 仍需操作者设置目录和文件 ACL，不能把这个模式数当作 Windows 权限证明。失败时保留明确路径的不完整加密文件，检查后另选新文件重试；不自动删除。目录应可信，不能保证抵抗已控制宿主文件系统的攻击者。

## 执行

在 `zhongyi-platform` 目录执行。先通过安全环境配置凭据、密钥；应用不会自动读取 `.env`。以下命令只展示路径和 schema，不包含秘密：

```powershell
# backup-store 是操作者预先建立且限制访问的目录。
npm.cmd run db:backup:postgres -- --schema food_education --output .local/backup-store/food-education-001.zfbackup

# 恢复到全新 schema，不覆盖、清空或切换原库。
npm.cmd run db:backup:postgres -- --restore --input .local/backup-store/food-education-001.zfbackup --schema food_education_recovered_001
```

编译入口为 `node build/tools/backup-postgres.js`，参数相同，先执行 `npm.cmd run build:server`。备份命令不采用运行服务的默认 schema，必须显式指定。已有 PostgreSQL v1/v2 应先按迁移文档显式升级；当前运行代码要求 v10，但仍接受 v3/v4/v5/v6/v7/v8/v9 备份。旧备份恢复后保持原结构，不能直接启动 v10 服务，须另行显式升级；不倒填历史迁移日志。恢复账号需要创建 schema/表/函数等权限，不能因此给应用运行账号长期授予管理员权限。当前专业图片持久化及真实PG测试接续见根`.refactor/evidence/photo-professional-storage-20261012/RUNTIME.md`，历史恢复记录不替代新版全量通过。

备份报告的 `encrypted=true` 仅证明工具完成加密文件写入，`recoveryVerified=false` 明确尚未恢复验证。恢复报告的 `verified=true` 表示新目标的完整业务行、两个历史表和序列逐项摘要核验通过，随后撤销所有恢复会话，并在 v6 结构追加新的发布冻结批次，再验证其余数据保持不变。`dataDigest` 为备份原数据，`restoredDataDigest` 为会话撤销及发布冻结后的实际数据，二者可不同；`sessionsRevoked`、`publicationFrozen` 和 `publicationFreezeVersion` 明示有意变更；旧结构没有发布功能，不补造冻结表。报告不输出行内容、账号散列、连接串或密钥。

## 恢复演练与切换

1. 保留原库、原文件和密钥，选择隔离的全新目标。输入文件先认证并完整校验，再连接目标；事务内重建可信结构并写入数据，任何外键/约束/逐行验证失败均回滚整个新 schema。已有目标拒绝覆盖，同名并发恢复只有一个可以成功。
2. 使用新目标启动隔离的应用实例，重新登录，并保持 `AI_EXTERNAL_ENABLED=false`。旧会话即使原本未到期也不能恢复使用；密码散列与角色原样恢复。备份之后的改密、禁用账号和许可撤回可能不在恢复时点内，管理员须核对并重新执行这些变更，再检查额度、考虑切换；安全事故恢复还需按事件处置要求轮换凭据。恢复历史许可不等于重新取得当前外传授权。
3. 检查目录、私有备注、来源固定引用/核验、审阅队列和公开接口隔离，保存一次测试写入并验证审计事件；重启数据库/应用后重查。来源核验和专业资格/意见仅恢复备份时点记录，不代表恢复时仍获认可，必须核对备份后撤销/到期/账号变更。v6 恢复已经写入新冻结批次；管理员恢复冻结状态之后仍需新批准与明确发布操作，旧指针不能自行复活。应用发布 API/页面已经接入，但服务端能力默认关闭，恢复操作不会启用公开内容。
4. 停写原服务，人工比较备份时点至故障时点的差异，确定可接受的数据损失窗口。只有确认完成后，才手动调整服务的 `DATABASE_SCHEMA`、重启并进行健康与业务验收。本工具不替操作者自动切流或撤回旧环境。
5. 定期将加密文件复制到受控异地存储，并建立保留期限、删除审批、恢复时间/数据丢失目标及失败告警。当前没有部署这些自动化设施；本机文件与一次测试不能证明异地灾备完成。

PostgreSQL 区分 SQL 导出、文件系统和持续归档等备份方式；完整生产方案需按部署规模选择并演练。[PostgreSQL 备份概览](https://www.postgresql.org/docs/18/backup.html)

## 工程验证

`npm.cmd test` 包含加密随机性、认证拒绝、正文/历史校验、独占文件和链接路径拒绝测试。`npm.cmd run test:postgres` 在真实独立 PostgreSQL 中验证业务捕获、全新目标恢复、旧登录失效、新登录 HTTP 读写、不可变历史触发器、并发写锁/并发恢复、约束失败整体回滚、历史 v3/v4 导入及旧 v3/v4/v5 备份兼容、实际与编译 CLI，以及完整数据库停机重启后的持久化。每轮真实结果写入 `.local/postgres-test-results.latest.json`；其中夹具停止状态必须实际确认。

这些证明的是本机工程恢复能力，不是已部署的备份定时任务、异地留存、生产 RPO/RTO、HTTPS、微信或真机验收。

### 本机验证问题记录 历史

以下 51/28 项和当时的观察期限为业务恢复首批历史；来源核验阶段曾覆盖 24 张业务表、旧 v3/v4 备份和五次重启，轮次见 [来源核验工程记录](source-verification.md)。当前 28 表发布治理与旧 v5 兼容的结果另见 [发布治理](publication-lifecycle.md)。现在观察同一拥有进程直到正常退出，不把单次观察期限当成终止信号。

首轮 27 组真实 PostgreSQL 测试通过，完整数据库重启 3 次。补充“导入后实际编辑再备份”和“未知字段拒绝遗漏”后的一轮为 27 通过、1 失败：最后一次关机观察超过控制器期限，未记成恢复通过。对应夹具 `cluster-NYcLAX` 日志记录检查点总耗时 252.139 秒，其中同步 249.982 秒，随后数据库自然退出；不是通过关闭 `fsync` 或强制停止处理。

同时发现旧清理路径可能在观察超时后再次请求同一进程停机。现改为共享单次停机 Promise，观察窗口到期不代表进程终止；完整退出前不启动另一个数据库，测试进程已结束则不执行迟到重启。测试侧验证期限调整为 10 分钟，持久性和业务断言未降低。最终重跑须同时检查完整重启、逐项数据校验和 `fixtureStopped=true`，不能只取前 27 组结果宣布全部通过。

修复后最终完整重跑：51 组普通 HTTP/SQLite/迁移/加密回归通过；28 组真实 PostgreSQL 测试通过、0 失败/跳过、完整重启 3 次，夹具 `cluster-dJdTWP` 已自然停止，报告为 `scope=migration-api-and-recovery`、`fixtureStopped=true`。类型检查、Web/API 构建及原小程序 `.10` 的 12 件版本制品校验通过。实际恢复覆盖导入后的备注/来源修订、恢复后新登录与 HTTP 写入、三种事件序列、历史引用、许可与额度；没有修改真实工作库。当前批次不改 UI，也未重跑 Edge 或微信真机验收。
