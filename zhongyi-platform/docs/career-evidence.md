## 面试需要讲清的关键问题

### 一次草稿保存如何落库？

沿着 `web/ContentEditor.tsx → web/api.ts → server/workflow-http.ts → server/workflow.ts → SQLite → JSON → React` 讲解。前端提交正文和 `expectedLockVersion`；API 校验输入、会话、Origin 与 CSRF；仓储在事务内再次验证当前权限和版本，将正文修订、固定来源引用、草稿头和事件一起提交。版本过期返回 409，页面保留输入，要求明确重新加载，而不是覆盖他人修改。PostgreSQL 使用对应异步仓储，见[内容工作流](workflow.md)。

`revision` 标识正文版本；`lockVersion` 还随提交、审阅等协作操作推进。只检查正文版本不足以发现状态已经改变。取消读取请求也不代表服务器写入已回滚；响应丢失时不能盲目重复提交。

### 为什么不能只在页面隐藏按钮？

直接调用 API 仍可能越权。服务器独立检查会话与角色，事务提交前重查当前授权；密码散列等异步操作期间撤权后也不能继续写入。Cookie 负责认证，CSRF 令牌不是独立登录凭据。参考[账号与权限](authentication.md)及 `server/auth-http.ts`。

### 请求超时是否表示保存失败？

不表示。React 共用请求层的 15 秒上限同时覆盖响应头和正文；取消只停止浏览器等待。数据库可能已经提交，而返回消息在途中丢失。因此读取可由用户重试，写入则提示结果无法确认、保留输入，先重新读取当前修订，不自动重发。明确的服务器 409、401 等拒绝仍按原错误处理，不能一律称作弱网。

沿着[请求层](../web/api.ts)解释每次调用独立的取消控制器、页面取消与截止时间的先后顺序，以及结束时清理计时器和监听器。对照[故障用例](../tests/browser/request-timeout.spec.ts)：真正通过 HTTP/SQL 保存测试备注，只截住返回浏览器的响应，再独立读取已提交修订，确认界面提示不确定且只发出一次写请求。完整实测结果见[等待与提交核对](web-request-recovery.md)，不是线上网络或性能测量，也不是服务端事务取消、幂等键或恰好一次交付的实现证明。本人复现并能解释后再作为个人案例使用。

### 刷新失败为什么不能显示没有编辑记录？

没有读到结果与成功读取空数组不是同一状态。工作台共同读取目录、统计和记录；请求开始后隐藏旧记录与统计，失败显示暂不可用，只有本轮完整成功才展示数量或空结果。已打开备注和未保存输入独立保留，不因只读刷新丢失，也不自动重发写入。

可沿着[读取状态修复](audit-read-recovery.md)解释共同响应、取消旧请求和独立输入状态，并亲自复现延迟读取、网络失败、明确重试。三个新用例在旧界面均失败，修复后SQLite与真实PostgreSQL完整页面各44项通过；这些数字不并入平台单元测试，也不是线上可用性或微信验收。本人理解状态划分与取舍后再使用该案例。

### 发布状态刷新失败为什么不能继续显示旧批准？

旧快照仍是历史内容，但旧批准不一定仍有效。管理页在读取或写入核对尚未结束、或出现错误时隐藏旧发布状态和历史展示，保留未提交输入并禁止继续操作；重读只发GET，不自动重发可能已经提交的操作。服务端仍独立检查权限、修订和固定依据，隐藏页面不是权限控制的替代品。

可沿着[发布管理读取与失败恢复](publication-read-recovery.md)亲自复现已提交冻结后刷新失败、输入保留与数据库只追加一次。页面组的隔离工程模拟不证明真实专业批准或正式内容已经上线；理解代码并完成复演后再作为个人面试案例使用。

### 为什么选项查询重试不能刷新整个编辑器？

搜索词、选中的固定对象和未提交输入是不同状态。食材或来源列表失败，只使这份选项列表不可用，不应清空已经打开的意见；局部重试只重读该列表。详情失败则不能继续显示旧资格或专业状态，保留输入并停用操作，明确重读成功后才替换。管理员的资格读取还依赖账号列表确认，前一步失败不能被后一步成功掩盖。

沿着[协作审校读取与输入保护](governance-read-recovery.md)解释独立错误、取消检查、只读重试及依赖读取；亲自复现查询失败、输入保留、零写请求和数据库记录前后一致。共用读取Hook只管理GET，不是服务端事务取消、幂等写入或真实资格认证。工程在AI辅助下完成，能够解释并复演后再作为个人案例使用。

### 为什么请求已完成，页面仍可能一直显示加载？

客户端请求状态与页面生命周期是两个独立状态。首页离开时旧观察令牌必须失效，但返回时若仅读取一次仍在加载的状态，原请求结束后又没有当前观察者，界面就会卡住。修复通过只读访问已有Promise并为当前页面建立新令牌，不在返回时重新联网；旧页面、旧会话、删除前令牌仍不能更新界面。

沿着[小程序读取返回恢复](../../zhongyi/docs/catalog-read-lifecycle.md)复现“开始读取→隐藏→返回→交付原结果”，解释请求去重与观察者替换的区别。11项受控专项覆盖成功、失败、截止、删除及红旗；既有[跨工程用例](../tests/public-catalog.test.ts)使用真实HTTP/SQL结果延迟交付，不把Node微信接口模拟称作真机体验。本人能够复现和解释后再将其作为个人排错案例。

### 为什么来源和审阅必须固定版本？

来源修订不能悄悄改变已引用的证据。正文、来源和审阅意见各自绑定固定版本与摘要；新正文不能继承旧专业通过意见。自审检查读取完整参与历史，不以页面最近 20 条替代。编辑通过仍为私有，公开还需要独立专业意见、来源核验、发布批准及明确发布。参考[发布生命周期](publication-lifecycle.md)。摘要证明的是数据一致性，不是事实正确或执业身份真实。

### SQLite 和 PostgreSQL 怎么取舍？

SQLite 便于本机单进程演示，当前 Node SQLite API 有实验性边界。PostgreSQL 使用独立连接处理异步事务；现有写入锁策略面向低频内容管理，不据此宣称高并发或高 QPS。两者都需验证迁移、重启和权限，而不是换一个连接串就算兼容。参考[数据库运行](postgres-runtime.md)和[架构取舍](architecture.md)。

### 普通重启与备份恢复有什么区别？

普通重启保留未过期会话和数据；退出、账号撤权会主动撤销会话。PostgreSQL 加密业务恢复先核验完整数据，再撤销旧会话并追加发布冻结，恢复到新目标且不自动切换工作库。此流程不是高可用、WAL/PITR 或容器灾备的证明，参考[备份恢复](backup-recovery.md)。

### 服务有 HTTPS，数据库连接就安全吗？

不是同一条链路。浏览器到 Express 的 HTTPS 不保护 Express 到 PostgreSQL 的连接；后者还需配置数据库 TLS，并同时验证签发链和 URL 主机名。只开启加密但关闭证书或名称检查，不能确认连到预期服务器；连接失败也不能悄悄回退明文。

项目连接池限定 `verify-full`，拒绝弱校验和参数覆盖，并把真实握手检查纳入完整 PostgreSQL 验收。可沿着[连接策略](../server/postgres-migration.ts)、[四项真实连接测试](../tests/postgres-tls.test.ts)与[配置及运行证据](postgres-transport-security.md)解释：可信 CA 下读取当前会话加密状态，随后分别验证缺少 CA、主机名不匹配和明文连接被拒绝。生产共享连接池现强制明确的严格 TLS 配置，服务和操作者工具一致；非生产演示仍允许显式明文。最小数据库权限、数据库整体访问策略和公网部署不因此完成；本人复现并理解后再用作面试案例。

联合 HTTPS 套件另检查七次编译应用启动的实际 SQL 加密连接，排除观察工具自身，并把三种数据库拒绝检查接入同一轮。它与完整迁移/恢复套件分别验收，不能把两份历史通过报告拼成同一部署证明；实际终态见[两段连接检查](https-runtime.md#https-与数据库-tls-同轮检查)。这种验证方法可解释“配置了 TLS”和“应用确实使用 TLS”的区别，不代表已上线或具备生产最小数据库权限。

### 应用角色与数据库角色如何分工？

应用内 admin、editor、reviewer 依赖会话、服务端权限与事务内重查；数据库运行账号服务于整个API，不能把它当成每个用户的独立数据库权限。迁移所有者负责结构，运行账号按清单读取目录、维护当前状态并追加历史，不拥有表、不能改结构或重置审计序列。生产仓储用自身连接执行只读启动门禁，固定系统搜索路径，拒绝所有者、认证身份切换及额外/缺失权限，不自动修复。受限账号下的编译API、实际越权/授权回滚与HTTPS联合验证见[权限分离](postgres-runtime-permissions.md)。[容器凭据入口与独立编排](container-credential-separation.md)已按命令分开两份文件；主机测试不证明容器秘密实际挂载、引擎运行或数据库整体访问策略，不能描述为完成了生产数据库安全。本人应复现一次正常保存和一次越权拒绝后，再把它讲作个人工程经验。

### AI 在哪里，哪些尚未验证？

AI 是可选编辑辅助，不负责诊断、开方或发布。原文检索、固定引用、逐字核对与人工采用有离线契约；采用只更新未保存输入，不自动保存、改安全字段或发布。真实外部模型调用为 0，42 例离线契约不是模型准确率或费用测量。参考[编辑辅助](assistant.md)。

### 能讲述哪些排错案例？

新增[HTTPS登录超时诊断](https-request-diagnostics.md)可用于解释如何区分TCP、可信TLS、响应头与正文阶段，以及为何没有响应编号时只能给出时间窗口候选。随后[隔离SQL测量与事务优化](sqlite-login-transactions.md)把双份限流计数改为一次提交，保留账号限流仍计入IP和错误回滚保护。不同轮次耗时不能全归因于修改，历史超时缺少内部时序；不能写成“彻底解决性能瓶颈”或编造优化比例。三类故障注入证明诊断分类，不是线上性能或稳定性测量。

可结合[数据库退出观察记录](database-test-reliability.md)解释为何要同时观察真实进程退出与日志结束，而不能只靠 IPC 汇总事件；未证实的旧停滞原因不要讲成已定位。另一案例是共享浏览器输出目录导致两张旧截图丢失，修复后改为每轮 UUID 隔离，并比对后续运行前后的截图摘要；旧图未恢复，新图不能冒充历史证据，见[截图隔离记录](continuous-integration.md#完整页面复核与截图隔离)。只有本人理解并复现后，才可描述为个人排错经验。
