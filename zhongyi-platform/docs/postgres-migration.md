# SQLite → PostgreSQL 迁移

## 当前交付范围

已实现只读 SQLite 快照、PostgreSQL 结构、事务导入、逐行摘要校验和独立迁移记录。支持 SQLite v3 至 v12 的 16/18/21/23/24/28/29/30/31/32 张业务表；v4 增加原文摘录和辅助调用元数据，v5 增加许可历史、每日额度策略和调用授权，v6 增加专业资格核验/固定意见，v7 增加来源核验，v8 增加固定快照、批准、发布事件和冻结历史，v9增加图片核对意见，v10增加具名图片送审版本，v11增加独立图片权利审核，v12增加专业图片意见与资格/原图/核对/送审/权利的固定关系（均不授予公开资格）。保留目录版本、备注、账号散列、会话、限流、安全事件、来源版本、内容修订、固定引用、审阅任务及新增治理记录。

**默认 Web/API 运行库仍是 SQLite；现已提供显式 PostgreSQL 业务模式。** 迁移工具不自动切换运行库，仅设置 `DATABASE_URL` 也不会切库。目录、账号及完整私有编辑工作流的异步接入与启动配置见 [PostgreSQL 业务运行模式](postgres-runtime.md)。未对真实工作库执行切换。

迁移不改变内容审批历史，`editorial_accepted` 仍是私有编辑质量通过，不新增专业批准。若 SQLite v8 源库已有发布快照，逐行比较原始摘要通过后额外追加迁移冻结，绑定迁移编号与源摘要；`--verify` 单独核验这条冻结，再比对每一个原始字段。原导入摘要和计数不被改写，迁移不会使既有发布指针在新库自动生效。

## 使用

先按 README 安装依赖并导入受验证目录。需要一个真正可连接的 PostgreSQL 数据库，以及有建 schema 权限的迁移账号。通过当前终端或密钥管理工具配置 `DATABASE_URL`；不要在命令行参数、代码、截图或提交中放密码。本地应用不会自动加载 `.env`。

```powershell
npm.cmd run db:migrate:postgres -- --source .local/editorial.sqlite --schema food_education
npm.cmd run db:migrate:postgres -- --verify --schema food_education
```

也可构建后执行 `node build/tools/migrate-postgres.js`，参数相同。第二条只做迁移后的提交核验，不能代替业务切库测试，也不能在已有新业务写入后继续要求等于旧快照。

操作要求：

- 源库必须是 schema v3 至 v10 的普通 SQLite 文件。只读导出分别生成快照格式 v1/16 表、v2/18 表、v3/21 表、v4/23 表、v5/24 表、v6/28 表、v7/29 表或 v8/30 表，不升级旧源文件。未知表/字段、缺失版本、目录漂移、损坏外键、固定修订/许可/资格/审校/来源核验/发布历史摘要或关系不一致时拒绝迁移，不自动“修复”源库或忽略数据。
- 目标必须是全新专用 schema；默认不会选择目标。禁止 `public`、系统 schema 和不合法名称。已经存在的目标即使为空也拒绝覆盖；不要删除旧库来绕过此检查。
- 迁移前先完成源库备份，在切换窗口停止旧服务写入。工具取得一致性快照，但快照之后发生的旧库写入不会自动同步；当前不提供在线双写或增量迁移。
- 目标连接、数据库和凭据由操作者明确指定。本批测试只使用专用测试库，未对真实工作库执行切换。
- 正式部署还需 TLS、最小权限及独立迁移/运行角色、备份恢复、监控和 API 切换验收；本机测试不代表这些已经完成。

## 实现与保护

源库使用 `DatabaseSync(..., { readOnly: true })`，在读取事务内检查完整性/外键、精确表结构并导出。密码仅转移已有加盐散列；会话仅转移既有令牌散列及必要会话字段。迁移数据只存在进程和目标数据库中，不生成包含账号/草稿的明文 JSON 导出文件；CLI 输出只有摘要、版本、表数量和结果，不输出连接字符串、凭据、私有正文或账号清单。

PostgreSQL 导入从连接池取得一个专用连接，在同一事务中加目标级 advisory lock、确认 schema 不存在、建结构、参数化分批写入、检查约束、恢复自增高水位、逐行读回比较并登记结果。事务必须使用同一个客户端，不能将连接池的随机连接查询混入事务。[node-postgres 事务说明](https://node-postgres.com/features/transactions)

目标保留关系外键、角色/状态约束、固定版本关系和每条食材最多一个待审任务。来源、内容、引用历史，以及 PostgreSQL 迁移和导入记录的 UPDATE/DELETE/TRUNCATE 由触发器拒绝；这不是抵抗数据库超级用户或有 DDL 权限者篡改的保证。

`source_records` 的当前头需要与 `source_versions` 对应，使用延迟检查外键，以便在事务内先插入头再插入版本；提交前统一转为即时校验。时间和摘要参与的正文保留原始 TEXT 字节，不因 JSONB 重排或日期格式转换使历史摘要失效。

三个事件表迁移 SQLite 的自增高水位，而不只是当前 `MAX(id)`；空表下次 ID 为 1，非空或曾有记录的表继续递增。PostgreSQL 序列值一般不随事务失败回退，因此本工具只设置事务内新建 schema 的新序列，不改变已有目标的序列。[PostgreSQL 序列说明](https://www.postgresql.org/docs/current/functions-sequence.html)

BIGINT（如毫秒到期时间）只转换为 JavaScript 安全整数，超范围拒绝而不四舍五入。文本排序按 PostgreSQL `C` collation 与 SQLite BINARY 对齐。源/目标逐行摘要包括全部业务字段和序列，而非仅比较行数。

`postgres_migrations` 保存 PostgreSQL DDL 版本和校验摘要（当前最高 6）；原 `migrations` 保留 SQLite 1 至源库版本的历史时间（当前最高 8）。两者不能混为同一套迁移。`migration_runs` 保存导入摘要、基础目录摘要和表计数，不保存源文件路径或凭据。成功后 `--verify` 可重新连接验证已提交快照；新库开始业务写入后，这个快照是历史切换基线，不要求新内容永久等于旧库。

## 已有 PostgreSQL 的显式升级

当前新导入会在同一事务建立 PostgreSQL v1 至 v8，即使 SQLite 源库仍为 v3 至 v10，也不改写源摘要或补造新增表的历史数据。旧 PostgreSQL v1 至 v7 启动新业务代码会被拒绝，先备份并停止写入，再执行：

```powershell
npm.cmd run db:migrate:postgres -- --upgrade --schema food_education
```

升级不接受 `--source`，只对已经存在的明确目标追加尚未应用的 v2 至 v8 表、约束和日志；原版本 SQL 及已登记摘要保持不变。重复升级幂等，未知日志、校验摘要漂移或部分结构冲突时事务回滚，不 DROP/覆盖冲突表。升级同时协调导入锁和业务写锁，仍需由操作者安排停写窗口。v7新增不可变图片核对意见，不是审批；升级后须重新应用及核验运行角色对新表的SELECT/INSERT权限，再启动新版服务。 v8追加独立不可变图片送审版本及意见引用，新表同样仅SELECT/INSERT，不自动公开。

SQLite v3 至 v10 导入记录继续分别按16/18/21/23/24/28/29/30表与快照v1至v8校验；结构升级不重写 `migration_runs` 或原导入摘要。旧版本不补造来源核验、专业资格/意见、许可变更或追溯扣减次数。已有新业务写入后，不用 `--verify` 要求回到旧基线。回退旧服务代码不等于数据回滚，需单独验证备份恢复。

`test:postgres` 使用开发依赖中的 PostgreSQL 原生二进制启动随机端口、SCRAM 认证、仅监听 `127.0.0.1` 的专用进程；不创建系统服务或系统用户，不改 WSL。平台二进制来自 `embedded-postgres` 的可选开发包，仅用于测试，不用于生产运行。[测试包说明](https://github.com/leinelissen/embedded-postgres)

前 7 组真实 PostgreSQL 迁移测试覆盖：

1. 当前 21 表逐行迁移、中文/emoji、密码散列验证、毫秒会话、固定 v1 引用、摘录/辅助元数据、许可历史、额度/授权与私有审阅状态。

5. 三个自增高水位和安全 BIGINT。
6. 实际 106 条目录的迁移，在 PostgreSQL 进程完全停机/重启后逐行验证。
7. CLI 的实际迁移、独立验证、编译后命令核验、重复目标/非法参数拒绝及输出不泄露凭据或私有正文。

其后继续验证实际 HTTP 业务、跨连接池并发、审计失败回滚、权限/会话撤销、最后管理员、持久化限流、公开目录漂移拒绝、新业务写入完整重启和编译后服务启动。浏览器另行连接真实 PostgreSQL 验证 React 全链路，见业务运行说明。

P3 增加真实 v1/v2 → v3 显式升级/幂等/回滚、旧 16/18 表摘要与原 DDL 保留、新表不可变/外键和 HTTP 辅助链路；两个连接池竞争调用占位、当日计数及许可修订，不一致实例策略拒绝，许可撤回再授权后旧任务结果仍拒绝。第三批另验证摘要模式复用固定来源、额度与私有边界，摘要终态元数据完整重启后保留，不保存输出正文到调用审计。模拟模型明确标注，不计为真实 AI 调用。2026-10-08 当前真实 PostgreSQL 21 组通过，实际完整进程重启 2 次，许可与计数保留；普通 HTTP/SQLite/迁移源/适配器回归共 47 组通过。

结果摘要保存在 `.local/postgres-test-results.latest.json`，包含实测 PostgreSQL 版本、通过/失败数和实际重启次数。进程正常停止，专用 `.local/postgres-tests/cluster-*` 证据目录保留且忽略提交；不自动递归删除它们。测试 SQLite 文件是独立生成的数据，逐项校验后清理，不修改真实工作账号或备注。

Windows 的完整停机可能等待磁盘同步。控制器只发送一次正常快速停机，共享同一停机 Promise；`pg_ctl` 初次观察 60 秒到期后仍等待同一个拥有进程正常退出，定期输出观察状态，不重复发信号或以新实例代替。测试侧回执观察期限到期也不能当作停机完成，仍须结合进程、日志及最终 `fixtureStopped=true`；业务连接超时、持久性和校验断言未因此放宽。
