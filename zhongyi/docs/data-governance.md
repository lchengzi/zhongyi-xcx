# 数据治理规范

## 1. 治理目标

每条展示给用户的信息都应回答四个问题：它是什么、当前是否允许作为食品使用、对谁或在什么条件下有限制、结论来自哪里。无法回答时应显示“未知/待核实”，不得用默认值掩盖缺口。

数据规模本身不是安全验收条件。当前内容版本保存 87+6+9+4 的独立官方名称快照，并以 106 条作为该版本的完整性断言；它不能被解释成未来目录的永久总数。官方目录新增、修订、撤回或解释文件变化时，应建立新版本与新快照并重新审核，不能为了让旧断言继续通过而忽略变化。

## 2. 来源优先级

从高到低采用：

1. 国家法律法规、国务院部门规章及国家卫生健康委员会等主管部门公告；
2. 官方公告解读、官方食养指南、国家标准或药典中与当前字段直接相关的内容；
3. 省级主管部门公开文件；
4. 经过编辑委员会批准的专业教材或同行评议资料，仅用于补充知识，不得覆盖上级来源的法规身份和限制；
5. 商业页面、自媒体、搜索摘要和模型生成内容不得作为事实字段的唯一来源。

来源记录至少包含标题、发布机构、文件号或稳定标识、发布日期、URL、状态和访问/复核日期。涉及拉丁学名、物种、部位、限量或特殊人群时，应尽量把来源关联到具体字段，而不是只给条目级参考文献列表。

当前数据包中，来源记录的 `status` 只描述该文件本身，允许值为 `published / superseded / withdrawn / unreachable`；它不能代替材料的法规状态。每个嵌入来源都必须同时具有 `publishedAt` 与 `checkedAt`，法规、安全和食用形态中的 `sourceIds` 必须能解析到该条目嵌入的来源记录。链接不可达或文件被撤回时，不得继续把相应字段标为已核验。

## 3. 最小数据契约

实现可以扩展字段，但不得删去以下信息类别：

```text
identity
  id                     稳定、唯一、不可复用
  name                   规范中文名
  aliases                别名数组，可为空
  latinName/species      拉丁名或物种身份
  family                 科属信息（资料不确定时为 unknown）
  ediblePart             获准或被讨论的具体部位

regulatory
  status                 current / superseded / withdrawn / unknown
  category               ordinary_food / food_medicine / professional_only / unknown
  foodUseRestriction     食用范围、部位、用量或用途限制；不得从相似材料推断
  sourceRefs             指向来源记录

safety
  pregnancy              yes / no / unknown
  lactation              yes / no / unknown
  infantChild            yes / no / unknown
  allergy                 通过规则数组 + 审校状态表达
  liverKidney             通过规则数组 + 审校状态表达
  medicationInteraction  通过规则数组 + 审校状态表达
  notes                   可追溯的限制说明

review
  evidenceStatus         verified / partial / unknown
  reviewedAt             ISO 日期
  reviewedBy             由结构化审核记录派生的角色摘要，不作为独立放行证据
  contentVersion         可回溯版本号
```

应用层可采用等价的扁平字段或枚举命名，但必须保存这些语义，且静态检查器所需的核心安全状态不得用布尔值代替。

## 4. 三态规则

- `yes`：有直接来源支持该特定人群在所述食品范围内适用；不能仅因没有检索到风险而填写。
- `no`：来源明确不推荐，运行时作为硬阻止。
- `unknown`：未找到足够资料或尚未审校。

条件性慎用不挤进三态字段，而是放入 `cautionConditions`、相互作用或加工注意事项等可解释规则数组。运行时仅为兼容旧数据防御性识别 `allow/avoid`，生产数据包的静态检查只接受 `yes/no/unknown`。

五个人群字段中任一值只要不是 `unknown`，都必须绑定当前状态为 `published` 的直接字段级来源；正向 `yes` 还必须完成中医、药学、合规三份结构化专业审核。来源撤回、不可达、字段引用为空或仅把审核状态改成 `reviewed` 时，运行时和详情展示均降为 `unknown/待确认`，不得显示“来源明确：适用”。

禁止用 `Boolean(value)`、`!!value` 或空值回退为 `false` 处理安全字段。缺失、未知、资料相互冲突都要进入 `unknown` 或阻止发布。前端排序不得把 `unknown` 当作 `allow`。

## 5. 审校与变更流程

1. 采集者保存原始文件、稳定链接和结构化摘录。
2. 编辑者完成规范名、物种、部位、法规状态和限制的录入。
3. 医学/药学审校者检查传统资料与安全表述；法规身份由合规审校者确认。
4. 自动检查验证必填字段、唯一 ID、枚举、来源协议、日期和禁止措辞。
5. 发布人记录数据版本、应用版本、变更摘要和审核角色。
6. 发布后定期复核官方来源；发现撤回、纠错或风险更新时，优先下架相关条目，再完成修订。

同一人不应同时完成高风险字段的录入和最终批准。紧急纠错允许先下架后补齐记录。

任何安全子字段从 `pending / identity_only / partial` 改为 `reviewed` 时，条目必须同时具有已完成的专业审校、已核验来源及安全字段级来源引用；仅改枚举值不能消除“待审校”提示。食用形态映射标为 `reviewed` 时同样必须绑定字段级来源。

材料的 `professionalReviewState: reviewed` 不能由单一布尔状态或自由文本 `reviewedBy` 放行。每条材料至少需要 `tcm_clinician`、`pharmacist`、`compliance` 三个独立结构化审核记录；每条记录使用唯一 `reviewId`，绑定审核日期、当前目录 `contentVersion`、当前 `rulesVersion` 和排除审核元数据后的材料内容摘要。`audit.ingredientDigest` 必须由构建检查器对当前身份、法规、食用、安全、传统资料和来源内容重算；任一内容或规则变化都会使旧记录和整方材料行失效。现有 106 条尚未取得真人签审，因此 `reviews` 保持空数组、`ingredientDigest` 保持 `null`，不得用占位签名消除门禁。

## 6. 版本、撤回与追溯

- 数据包包含生成时间、内容版本和条目数，条目数只作为统计。
- ID 一经发布不得赋给另一种材料；名称变化通过别名和变更记录处理。
- 指南的发布日期与材料法规事件必须分开保存。旧指南中的当时限制作为 `historicContext` 原文留存，当前状态由后续有效公告更新；不得静默改写旧指南，也不得让旧备注覆盖较新的有效公告。
- 对存在先后公告的材料，详情页应能显示法规事件时间线、当前结论及其直接来源。
- 来源失效不自动意味着事实失效，但该条目进入待复核状态。
- `withdrawn` 或无法确认法规状态的材料不得进入普通筛选结果。
- 每次构建应可追溯到输入数据版本；禁止直接在生成文件中手工修正。
- 回滚应恢复数据包和与之匹配的规则版本，不能只回滚其中一方。
- 规则版本必须唯一映射到红旗、画像归一化、筛选、材料/整方门禁、摘要和公开构建代码的规则包摘要；规则代码变化而版本号不变时禁止登记新 release。

## 7. 隐私与最小化

小程序新增的公开目录读取是用户主动触发的固定 GET；不发送搜索词、收藏/对照 ID、安全问项或健康画像，不持久化服务响应。访问网络可能产生 IP、请求时间和标准访问日志，不能宣传完全匿名；后续部署须明确日志保留策略。健康会话仍只在本次小程序内，隐私删除会取消进行中的读取并清空公开资料缓存。公开目录只来自受摘要校验的已导入历史快照，后台来源、备注和编辑质量通过的草稿不能通过该接口公开。契约、失败回退和验证范围见 [公开目录与离线回退](public-catalog-api.md)。

P1 只持久化收藏和对照的条目 ID，存储键统一使用 `zhongyi_` 前缀；不采集姓名、手机号、病历、精确位置或自由文本症状。通用确认清单、症状/红旗、年龄与孕哺问项、用户主动填写的过敏物、基础疾病和在用材料名称，以及官方方案的已确诊目标确认，仅保存在本次小程序进程内，不调用 `wx.setStorageSync`、不上传，也不得写入日志。退出进程后这些会话数据清除；候选或安全画像变化时，确认清单和确诊目标确认立即失效。

安全页提供用户可见的“本地数据与隐私”入口。页面只显示收藏、对照、清单和确认项的数量或有无状态，不回显健康明细。一键删除必须执行并验证以下闭环：

1. 枚举并删除当前及旧版本所有 `zhongyi_` 持久化键，而不是仅把数组写成空值。
2. 将安全画像恢复为显式 `unknown` 和空数组，清空红旗、症状、过敏、疾病、用药、清单以及确诊目标确认。
3. 只有在存储删除可验证且会话摘要归零时才提示成功；删除失败不得误报成功，并应允许重试。
4. 成功后重新打开首页并重置页面栈，防止页面缓存或未提交表单恢复已删除内容。

用户主动复制的咨询准备会进入系统剪贴板。一键删除只负责本小程序管理的本地键和内存会话，不能删除已粘贴到其他应用的副本；该边界必须在隐私页明示。

如后续引入账号、云同步、分析或问卷，应在开发前完成个人信息影响评估，明确目的、最短保存期、访问控制、删除机制和单独同意；敏感健康信息不得为了推荐便利而默认上传。

## 8. 官方完整方案契约

完整方案与单味材料分层保存。每个方案必须具有稳定 ID、修订号、主来源、章节和页码定位、完整材料行、有序制作步骤、原始食用方式、内容版本及规则版本。

- `bundle.atomic` 必须为 `true`，删除、替换、增补、重排或按人数换算均为禁止。
- 每个材料行必须保留来源名称、部位、处理方式和原始用量字符串；普通食品同样需要统一身份记录，不能用自由文本绕过逐味审校。
- 普通食品材料使用独立 `externalFoods` 登记，不得写入或覆盖 106 条官方食药物质目录。配方“出现证据”只绑定来源名称、原量和材料行，不能复用为身份、法规、食用形态或安全直接来源；两类来源必须结构化分离。
- 外部材料行与 `occurrenceEvidence` 必须按 `foodId + recipeId + lineId` 双向一一对应。母鸡/鸡肉、葱/葱花、粳米/粳米粉、泛称油/香油等不同来源形态不得为了减少记录数而合并。
- 官方资料未给出的水量、火候、时间、频次、疗程或替代方式不得补写。
- 方案主来源决定整方内容，后续公告或安全来源只能追加限制和历史语境，不能静默改写原方案。
- `published` 必须同时满足整方内容、中医、药学、营养、合规和最终发布审核；每个角色都要使用独立审核记录 ID，绑定审核日期、当前内容版本、规则版本、来源文本摘要和当前整方摘要。每个已审安全域必须具有非空字段级来源。任一材料版本或安全规则变化后旧审核失效。
- `draft / reviewed / superseded / withdrawn` 均不得显示材料、用量和制作方法，也不得产生可操作详情按钮。
- 完整审校底稿 `data/recipes.js` 必须在上传配置中排除；`npm run build:recipes` 只把已发布整方的锁定内容写入公开索引。未发布记录在公开索引中只能保留名称、来源定位、目标边界、安全人群状态和审校进度，不得携带材料行、用量、步骤或食用方式。静态检查必须比较底稿与公开索引，并把任何过期或内容泄露视为构建失败。

当前 P3 的五个方案均为 `draft`。18 条配方普通食品登记只完成稳定 ID 与原文出现绑定，身份、法规、安全和专业签审仍未完成；运行时与静态检查均应返回可发布方案数 `0`。详见 `external-food-registry.md`。
